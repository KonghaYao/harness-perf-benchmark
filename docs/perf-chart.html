                        25 倍多）、进程树 CPU 均值 69.9% / 峰值 229.3%（两项都最高）、进程树 RSS 均值
                        798.9MB / 峰值 943.0MB（第二高的 Claude Code 才 274.9 / 321.9MB，差 2.9 倍）；按
                        「端到端 × CPU 均值」估整段消耗约 27 核·秒，其余五家 1.0~5.0 核·秒。继续混在榜单里
                        只会拉长横轴、把其余五家压成一堆，故后续批次不再跑它、不计入排名；代码
                        与沙盒保留在 playground/opencode/，历史读数也照旧留在图里（虚线那条）。
                        详见 docs/perf-compare.md。

  • 
                        一个 harness 一条线：线的右端就是它退出的时刻；各家的端到端
                        时长能差一个数量级，所以横向长度本身就是结论之一。
                    
    • 
                    
  • 
                        虚线是「首个请求」与「末次请求」（mock 侧记的时刻挪到采样时间轴上）。
                        虚线右边曲线还在、却几乎零 CPU，那就是收尾等待——peri 固定等 5.1s、
                        Codex 固定等 10.1s（退出时向 chatgpt.com 发请求、本机 DNS 污染导致超时），
                        与轮数无关；其余各家的收尾都在 0.2s 以内。详见
                        docs/perf-compare.md。
                    
    • 
                    
  • 
                        请求数 ≠ 轮数：mock 请求里混着各家自己的辅助请求——peri 的
                        「预测下一步输入」、opencode / dsh 的标题生成、pi 的上下文压缩总结。
                        辅助请求同样消费剧本条目，所以 100 条剧本下 opencode / dsh 实际只执行了
                        99 轮工具调用；pi 用的是 130 条剧本（它的压缩从第 70 轮起每轮多吃
                        一条），132 次请求里 100 次是主循环、30 次是压缩总结。
                    
    • 
                    
  • 
                        pi 的曲线中途会「变轻」：压缩之后它回传的历史被压成摘要
                        （请求体从 messages=200 量级压回 62 条），所以后半程的请求体与内存
                        不再随轮次增长——这是 pi 自己把上下文管掉了，不是漏跑。

                        口径默认「进程树」：Codex 的 CLI 只是 Node 启动器
                        （主进程 40MB 上下、CPU 近 0），真正干活的是它 spawn 的原生二进制，
                        切到「主进程」看 Codex 会严重低报。

                        CPU 是单核 100% 口径，多线程进程可以 >100%；内存取 RSS（含共享内存，
                        含工具调用的子进程时按进程树算）。

  • 
                        曲线默认按 1s 窗口做滑动平均（上面可切原始 / 0.5s / 1s / 2s）。
                        100ms 采样下多线程 harness 的 CPU 本就是锯齿：一轮里「拼请求、解析上下文」突发几拍，
                        等 mock 回包时几乎归零——本批数据里相邻两拍跳 30 个百分点以上的有 opencode 186 处、
                        dsh 25 处、Claude Code 8 处，那是真实读数，不是采样抖动；换 1s 窗口
                        后这些跳变全部降到 0 处（0.5s 窗口还剩 opencode 3 处）。所以平滑放在看图侧、不动原始
                        数据：表格里的均值 / 峰值与 samples.csv 始终是原始值，想看毛刺切回「原始」。
                    
    • 
                    
  • 
                        每条线的峰值上标了 harness 名（CPU 与内存都标）：圆点就是该家曲线的
                        最高处——平滑开着时标的是平滑后的峰值，想看原始峰值先把窗口切回「原始」；汇总表里
                        那列始终按原始读数算。名字默认写在峰值右侧，右边放不下时翻到左侧（内存峰值多半
                        落在收尾处，容易贴着右边界）。
                    
    • 
                    
  • 
                        内存的纵轴是反的（0 在顶、占用越大越靠下）：曲线往下走 = 内存变重，
                        方向与「负担加重」一致；CPU 轴仍是正常方向（越高越忙）。
                    
    • 
                    
  • 
                        机器上同时有别的工作负载时绝对值会偏高，横向比形状比数值更稳；
                        要更干净的数字就空机器上重跑，再生成一次 JSON。
