harness-perf-benchmark 榜单

长剧本：100 轮 × 约 4KB 正文 + 每轮一次工具调用，--exhausted stop 跑到自然结束。 开头是统一计分Beta：把 CPU 与内存按 1:1 折成一个数——CU = 1.0×核·秒 + 1.0×GB·秒 （公式结构借自阿里云 FC 的「资源使用量 × 转换系数」，系数是本项目定的），再折成批内百分制； 另给一列不折算的峰值（最坏一刻要占多少）。接着是柱状概览： CU 与两个峰值各一排横条，条短的是省的。口径与系数只在 scripts/perf/score.ts 一处。还在 Beta：口径没定稿， 拿它看趋势可以，别把名次当结论——两处取舍（后代 CPU 算不算、时长怎么算）还没讨论完。 下半部分是逐拍曲线：x 为相对时间（采样起点算 0），y 由按钮切换，曲线默认按 1s 窗口平滑（可切回原始）；每条线的峰值标了 harness 名，内存的纵轴是反的 （占用越大越靠下）。数据来自 data/perf-chart.json。

                        100ms 采样下多线程 harness 的 CPU 本就是锯齿：一轮里「拼请求、解析上下文」突发几拍，
                        等 mock 回包时几乎归零——本批数据里相邻两拍跳 30 个百分点以上的有 MiniMax Code
                        21 处、Claude Code 3 处、dsh 3 处、pi 1 处（peri / Codex 各 0 处），
                        那是真实读数，不是采样抖动；换 1s 窗口后这些跳变全部降到 0 处
                        （0.5s 窗口同样为 0）。所以平滑放在看图侧、不动原始数据：表格里的均值 / 峰值与
                        samples.csv 始终是原始值，想看毛刺切回「原始」。

  • 
                        每条线的峰值上标了 harness 名（CPU 与内存都标）：圆点就是该家曲线的
                        最高处——平滑开着时标的是平滑后的峰值，想看原始峰值先把窗口切回「原始」；汇总表里
                        那列始终按原始读数算。名字默认写在峰值右侧，右边放不下时翻到左侧（内存峰值多半
                        落在收尾处，容易贴着右边界）。
                    
    • 
                    
  • 
                        内存的纵轴是反的（0 在顶、占用越大越靠下）：曲线往下走 = 内存变重，
                        方向与「负担加重」一致；CPU 轴仍是正常方向（越高越忙）。
                    
    • 
                    
  • 
                        系数为什么是 1:1：FC 的 0.15 CU/(GB·秒) 等于说
                        「1 个核 ≈ 6.67 GB」（AWS Lambda 新版价 ≈ 7.6、Cloud Run ≈ 9，行业都在这条线上），
                        那是云厂商的出价。照它算，内存项在总账里只占 1%~8%，「谁更省内存」几乎不参与
                        计分（实测把内存权重压到 0，名次几乎不动）。本项目问的是资源负担，
                        就把这件事明说一次：1 核·秒 = 1 GB·秒，改系数只改
                        score.ts 里 CU_COEFFICIENTS 那一处。
                    
    • 
                    
  • 
                        机器上同时有别的工作负载时绝对值会偏高，横向比形状比数值更稳；
                        要更干净的数字就空机器上重跑，再生成一次 JSON。
